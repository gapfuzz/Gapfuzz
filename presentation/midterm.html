45초. 저희가 만든 건 네 가지 기능입니다. 첫째 진단은 라이브러리 공개 API마다 퍼징 중에 불렸는지, 안쪽 분기까지 다 실행됐는지 표시합니다. 둘째 원인 추적은 막힌 조건에서 거슬러 올라가 하네스의 줄과 인자까지 짚어 고칠 곳을 제안합니다. 셋째 검증은 고친 하네스로 같은 조건의 퍼징을 다섯 번 반복해서 막혀 있던 분기가 정말 열렸는지 셉니다. 일부러 안 고친 제안을 대조군으로 둡니다. 넷째 크래시 귀속은 크래시가 하네스 실수인지 라이브러리 결함인지 가립니다. 오른쪽은 진단 예입니다. 상태 기반(stateful) 하네스는 저희가 새로 만든 하네스로, 입력의 뒷부분으로 “어떤 연산을 어떤 순서로 할지” 고릅니다. 퍼저가 바이트만 바꿔도 호출하는 기능과 순서가 바뀝니다.

40초. 핵심인 원인 추적입니다. 한쪽으로만 간 조건문에서 시작해서, 그 조건이 읽는 값이 함수 매개변수면 그 매개변수로, 필드면 그 필드를 설정하는 생성자나 대입문으로 거슬러 올라갑니다. 그리고 하네스의 호출 지점에서 그 인자를 어떻게 넘기는지 봅니다. 예를 들어 XMLPrinter의 이스케이프 옵션 분기가 막힌 건, 하네스 170행이 네 번째 인자를 안 넘겨서 항상 기본값이었기 때문입니다. 판정은 다섯 가지이고, 인자를 고정했거나, 설정 API를 안 불렀거나, 값의 범위를 좁힌 경우가 하네스에서 고칠 곳이 됩니다.

3. 중간 결과 ① 도구 효과

하네스 효과와 도구 효과를 나눠서 봅니다

TinyXML2, 하네스마다 1시간 × 10회와 24시간 × 1회. 같은 시드, ASan+UBSan, 커버리지는 라이브러리 소스만 집계했습니다.

하네스 효과 (OSS-Fuzz → 상태 기반)

라인 38.1% → 77.5% (10회 모두, p<0.0001). 상태를 쌓는 하네스의 효과이고 도구의 기여는 아님

도구 효과

gapfuzz 수정(제안 10개) 분기 79.8% → 83.1%, 라인 77.5% → 78.5% (10회 모두, p<0.0001). 연산 자동 생성(+15개)은 2분 × 5회로 분기 80.4% → 84.5%

24시간을 돌려도 차이가 그대로 분기 커버리지, 하네스마다 1회

상태 기반 하네스는 4시간 반쯤 80.2%에서 멈췄고, 하루가 지나도 gapfuzz 수정 하네스가 처음 10분 만에 낸 83.0%에 못 미쳤습니다. 둘의 차이인 분기 25개는 시간이 아니라 하네스 코드를 고쳐야 열립니다. 크래시는 둘 다 0건.

45초. 첫 번째 결과는 도구의 효과입니다. 왼쪽은 TinyXML2를 하네스마다 한 시간씩 열 번 돌린 결과이고 점 하나가 한 번입니다. OSS-Fuzz 하네스를 상태 기반 하네스로 바꾸면 라인 커버리지가 38%에서 77%로 오르는데, 이건 하네스를 새로 설계한 효과라서 도구의 성과로 보지 않습니다. 도구의 효과는 그다음입니다. 상태 기반 하네스에서 도구가 짚은 열 곳을 고쳤더니, 분기 커버리지가 80%에서 83%로 열 번 모두 올랐습니다. 오른쪽은 두 하네스를 24시간씩 돌린 결과입니다. 고치기 전 하네스는 4시간 반 만에 80%에서 멈췄고, 24시간이 지나도 gapfuzz가 처음 10분 만에 낸 83%에 미치지 못했습니다.

3. 중간 결과 ③ 도구도 틀립니다

새 라이브러리에서 오판이 나왔고, 규칙을 고쳤습니다

libyaml·expat 첫 분석: 하네스 탓이 아닌 분기를 하네스 탓으로

“고칠 곳”이 겨냥한 분기규칙 추가 전후

expat19개8개
기존 5개 라이브러리, 하네스 9개고칠 곳 목록 그대로

메모리 할당 실패 처리: if (!ptr) return NULL처럼 할당이 실패해야 열리는 분기. 하네스 인자로는 못 엶 → 새 판정으로 분리

json-c: 제안을 그대로 넣었더니 매 실행이 죽음

json_object_array_shrink(arr, -3);  // 제안: 음수도 넘겨 보라
// 라이브러리: 음수면 json_abort()로 프로그램 종료

크래시 귀속 → 하네스 버그  API가 입구에서 거부한 인자를 하네스가 넘김

예전 규칙은 “라이브러리의 assert”로 분류했습니다. 규칙을 보완해 하네스 탓으로 가렸고, 하네스는 0 이상만 넘기도록 고쳤습니다. 이 분기는 열면 프로그램이 끝나는 분기라 하네스로는 열 수 없습니다.

Claude에게 같은 제안을 맡겼을 때 (3번 모두)

“음수는 json_abort()로 프로세스를 종료시키는 잘못된 인자라 넘기지 않음”

남은 과제: “열면 종료되는 분기”를 제안 단계에서 미리 거르기

40초. 세 번째는 도구가 틀린 사례입니다. 새 라이브러리에서 오판이 두 종류 나왔습니다. libyaml과 expat에서는 하네스와 상관없는 분기를 하네스 탓으로 짚었습니다. 메모리 할당이 실패해야 열리는 분기와, 라이브러리가 내부에서 채우는 값에 달린 분기였습니다. 이 둘을 거르는 규칙을 넣었고, 기존 결과는 바뀌지 않았습니다. json-c에서는 제안 자체가 틀렸습니다. 음수를 넘겨 보라고 했는데, json-c는 음수를 받으면 일부러 종료합니다. 대신 크래시 귀속이 이걸 하네스 실수로 가려서, 잘못된 버그 보고로 이어지지는 않았습니다.
