45초. 저희가 만든 건 네 가지 기능입니다. 첫째 진단은 라이브러리 공개 API마다 퍼징 중에 불렸는지, 안쪽 분기까지 다 실행됐는지 표시합니다. 둘째 원인 추적은 막힌 조건에서 거슬러 올라가 하네스의 줄과 인자까지 짚어 고칠 곳을 제안합니다. 셋째 검증은 고친 하네스로 같은 조건의 퍼징을 다섯 번 반복해서 막혀 있던 분기가 정말 열렸는지 셉니다. 일부러 안 고친 제안을 대조군으로 둡니다. 넷째 크래시 귀속은 크래시가 하네스 실수인지 라이브러리 결함인지 가립니다. 오른쪽은 진단 예입니다. TinyXML2 공식 하네스는 공개 API 303개 중 261개를 한 번도 부르지 않습니다. 이건 퍼징을 오래 돌려도 해결되지 않습니다.

35초. 하네스 설계입니다. 공식 하네스는 입력을 받아 Parse 한 번 부르고 끝납니다. 저희 하네스는 오른쪽 순서로 만들었습니다. 공개 API 중 트리를 바꾸는 연산 22종을 고르고, 입력 앞부분은 XML로, 나머지는 연산 번호와 인자로 씁니다. API를 잘못 써서 가짜 크래시가 나지 않게 가드레일을 넣었습니다. AI 초안을 팀이 검토하고 ASan으로 돌렸더니 하네스 버그가 하나 나와 고쳤고, 이게 크래시 귀속 기능의 계기가 됐습니다. 고친 뒤 24시간 동안 크래시가 없었고, 하네스 코드는 전부 실행됐습니다.

보라색 세 판정이 “하네스에서 고칠 곳”이 됩니다(우리 하네스 11곳, 공식 3곳, 5회 모두 같음). 라이브러리 내부 호출을 거치는 값은 최대 8단계 거슬러 올라가 하네스 인자까지 연결합니다.

40초. 핵심인 원인 추적입니다. 한쪽으로만 간 조건문에서 시작해서, 그 조건이 읽는 값이 함수 매개변수면 그 매개변수로, 필드면 그 필드를 설정하는 생성자나 대입문으로 거슬러 올라갑니다. 그리고 하네스의 호출 지점에서 그 인자를 어떻게 넘기는지 봅니다. 예를 들어 XMLPrinter의 이스케이프 옵션 분기가 막힌 건, 하네스 170행이 네 번째 인자를 안 넘겨서 항상 기본값이었기 때문입니다. 판정은 다섯 가지이고, 인자를 고정했거나, 설정 API를 안 불렀거나, 값의 범위를 좁힌 경우가 하네스에서 고칠 곳이 됩니다.

3. 중간 결과 ① 도구 효과

하네스 효과와 도구 효과를 나눠서 봅니다

TinyXML2, 하네스마다 1시간 × 10회와 24시간 × 1회. 같은 시드, ASan+UBSan, 커버리지는 라이브러리 소스만 집계했습니다.

하네스 효과 (공식 → 우리 하네스)

라인 38.1% → 77.5% (10회 모두, p<0.0001). 상태를 쌓는 하네스의 효과이고 도구의 기여는 아님

도구 효과

gapfuzz 수정(제안 10개) 분기 79.8% → 83.1%, 라인 77.5% → 78.5% (10회 모두, p<0.0001). 연산 자동 생성(+15개)은 2분 × 5회로 분기 80.4% → 84.5%

24시간을 돌려도 차이가 그대로 분기 커버리지, 하네스마다 1회

우리 하네스는 4시간 반쯤 80.2%에서 멈췄고, 하루가 지나도 수정한 하네스가 처음 10분 만에 낸 83.0%에 못 미쳤습니다. 둘의 차이인 분기 25개는 시간이 아니라 하네스 코드를 고쳐야 열립니다. 크래시는 둘 다 0건.

45초. 첫 번째 결과는 도구의 효과입니다. 왼쪽은 TinyXML2를 하네스마다 한 시간씩 열 번 돌린 결과이고 점 하나가 한 번입니다. 공식 하네스에서 우리 하네스로 가는 38%에서 77%는 상태를 쌓는 하네스의 효과라서 도구의 성과로 세지 않습니다. 도구의 효과는 우리 하네스에 도구가 짚은 열 곳을 고친 버전입니다. 분기 커버리지가 80%에서 83%로, 열 번 모두 올랐습니다. 오른쪽은 같은 두 하네스를 24시간씩 돌린 결과입니다. 고치지 않은 하네스는 4시간 반에 멈췄고, 하루가 지나도 고친 하네스의 첫 10분을 따라잡지 못했습니다. 오래 돌리는 것으로는 못 여는 분기를 하네스 수정이 연다는 뜻입니다.

45초. 두 번째 결과는 일반화와 안정성입니다. 우리가 쓴 하네스만이 아니라 남이 쓴 OSS-Fuzz 공식 하네스에도 적용했습니다. XML, JSON, YAML 파서와 압축 라이브러리까지 여덟 개입니다. 도구의 제안 35개를 적용했더니 막혀 있던 분기 97개 중 85개가 열렸고, 일부러 안 고친 제안 열 개는 하나도 열리지 않았습니다. libyaml은 고칠 곳이 0개였는데, 공식 하네스가 파싱만 하고 다른 API를 아예 부르지 않아서입니다. 오른쪽은 안정성입니다. 다섯 번씩 반복한 결과를 회차마다 따로 셌더니, 고치기 전에는 다섯 번 모두 막혀 있었고, 열린 85개는 다섯 번 모두 열렸습니다. 우연히 열린 분기는 없었습니다.

남은 과제: “열면 종료되는 분기”를 제안 단계에서 미리 거르기

35초. 세 번째는 도구가 틀린 사례입니다. libyaml과 expat을 처음 분석했을 때 하네스 탓이 아닌 분기를 하네스 탓으로 묶었습니다. 메모리 할당이 실패해야 열리는 분기와, 라이브러리가 상태를 쌓는 객체의 필드에 달린 분기였습니다. 이 둘을 거르는 규칙을 넣었고, 기존 라이브러리 다섯 개의 결과는 그대로인 것을 확인했습니다. json-c에서는 제안대로 음수를 넣자 매번 죽었는데, 크래시 귀속이 하네스가 잘못된 인자를 넘긴 것으로 가렸습니다.

왜 믿을 수 있나

LLM 출력은 그대로 쓰지 않습니다. 열렸는지는 실제 퍼징으로 재고, 크래시는 귀속 규칙이 하네스 탓인지 가립니다. 이번 실험에서 컴파일 실패 1번을 걸러 다시 고치게 했습니다. 아직 막힌 분기를 알려 주자 두 번째 시도에 연 경우도 있었습니다(cJSON: 앞의 null 검사를 피해 안쪽 함수를 직접 부름).

하네스 코드는 외부로 나갑니다

Claude API를 쓰므로 하네스와 라이브러리 일부 코드가 Anthropic으로 전송됩니다. 공개 오픈소스라 문제없지만, 비공개 코드라면 로컬 모델로 바꿔 끼울 수 있게 호출 부분을 분리해 두었습니다.

50초. 마지막 결과는 이번 주에 붙인 기능입니다. 도구가 고칠 곳을 알려 주면 사람이 하네스를 고쳐 쓰던 단계를 Claude API에 맡겼습니다. 도구가 하네스와 제안, 막힌 분기의 코드를 보내면 Claude가 고친 하네스를 돌려주고, 도구가 컴파일하고 퍼징해서 노린 분기가 열렸는지, 크래시는 누구 탓인지 검사합니다. 실패하면 이유를 돌려주고 다시 고치게 합니다. 라이브러리 7개의 고칠 곳 45개를 모두 맡겨 보니 44개가 통과했고, 겨냥한 분기 108개 중 100개가 열렸습니다. 사람이 고쳤던 제안끼리 비교하면 97개 중 사람이 85개, Claude가 89개를 열었습니다. 중요한 건 LLM을 믿는 게 아니라 검사한다는 점입니다.
