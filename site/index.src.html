gapfuzz는 막힌 조건이 읽는 값을 거슬러 올라가 하네스가 넘긴 인자까지 연결합니다. 아래에서 실제 사례로 직접 확인해 보세요.

설정값에 음수를 넣어 보라는 제안을 적용하자 매 실행이 즉시 죽었습니다. gapfuzz의 크래시 귀속은 이를 하네스 버그(확신 강)로 판정했습니다. 라이브러리 API newCharReader가 잘못된 설정을 예외로 알렸는데 하네스가 그 예외를 받지 않았다는 근거와 함께입니다. 하네스를 고쳐 다시 돌렸고, 라이브러리 개발자에게 잘못 보고할 뻔한 일을 막았습니다.

기존 도구

Fuzz Introspector와 무엇이 다른가

OSS-Fuzz의 Fuzz Introspector는 프로젝트 전체를 다루는 성숙한 진단 도구입니다. 겹치지 않는 부분은 원인을 하네스 코드까지 내려가 짚는 단계와, 고친 뒤의 검증입니다. Fuzz Introspector의 공식 사례 문서에도 “콜 트리를 보면 인자가 항상 상수로 고정돼 있다”는 원인을 사람이 찾아내는 과정이 나옵니다.

Fuzz Introspectorgapfuzz
알려 주는 것어느 함수·분기가 막혔나, 새로 노릴 함수하네스의 어느 줄, 어느 인자 때문에 막혔나
막힌 원인위치까지 제시, 원인은 사람이 판단고정 인자, 좁은 값 범위, 안 부른 API 등으로 자동 분류
고친 뒤다시 돌려 보고서 비교제안 단위로 막힌 분기가 열렸는지 대조군과 함께 검증
크래시다루지 않음하네스 실수와 라이브러리 결함을 자동 귀속
범위OSS-Fuzz 프로젝트 전체, 여러 언어C/C++ 라이브러리의 공개 API

한계와 계획

아직 못 하는 것과 최종 발표까지 할 일

  • 호출 순서와 상태에 달린 분기는 아직 원인을 짚지 못합니다. 예: 노드를 트리에 붙이지 않은 채 문서를 비워야 열리는 분기.
  • 원인을 잘못 묶는 경우가 있습니다. zlib에서 라이브러리 내부 지역 변수를 하네스 인자 탓으로 묶었고, null을 넘겨야 열리는 분기에 “값을 바꾸라”고 제안했습니다. 제안이 겨냥한 분기 97개 중 열리지 않은 12개는 이런 오판이거나, 앞선 조건이 먼저 걸러 내 하네스로는 닿지 않는 분기, json-c처럼 열면 라이브러리가 일부러 종료하는 분기입니다.
  • 새 라이브러리마다 규칙이 더 필요했습니다. libyaml과 expat에서는 처음에 메모리 할당 실패 처리 분기와 라이브러리가 상태를 쌓는 객체를 하네스 탓으로 잘못 묶었습니다(규칙을 넣기 전 “고칠 곳”이 겨냥한 분기: libyaml 169개 → 0개, expat 19개 → 8개). 규칙 두 개를 더해 고쳤고, 기존 라이브러리 5개의 결과는 바뀌지 않았습니다.
  • 정답을 도구를 만든 저희가 달았습니다. 표본도 작습니다. 팀원이 도구 판정을 가린 채 다시 답니다.
  • Claude가 고친 하네스도 사람이 읽고 넣어야 합니다. 검사는 60초 × 2회 짧은 퍼징이고, 하네스와 라이브러리 일부 코드가 Anthropic으로 전송됩니다.
  • 이 사이트에서는 분석을 직접 돌릴 수 없습니다. 미리 분석한 라이브러리 8개와 올린 결과 파일만 보여 줍니다.
  • Fuzz Introspector와의 정량 비교는 간이 방식으로만 했고, 새 버그는 아직 없습니다(최신 버전 3개를 1시간씩 퍼징, 크래시 0건).
1–2주

팀원 독립 라벨링도구 판정을 가린 시트로 두 명이 각자 정답을 달고 일치도를 잰 뒤 정확도를 다시 측정

2–3주

LLM 연동 확장지금은 고칠 곳을 하나씩 Claude에게 맡깁니다. 호출 안 하는 API의 연산 추가와 처음 보는 라이브러리의 하네스 초안까지 넓히고, 데이터가 밖으로 안 나가는 로컬 모델과 비교

3–4주

놓치는 원인 보완, 기존 도구 비교호출 순서·상태 의존 분기와 잘못 묶는 경우를 원인 추적에서 고치고, Fuzz Introspector 정식 방식과 같은 하네스로 대조
